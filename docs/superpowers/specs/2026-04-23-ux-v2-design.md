# UX v2 — Search, record detail, live filter, help, pause, level toggle, auto-reconnect, JSON highlighting (UI + TUI)

**Status:** accepted design, awaiting implementation plan
**Date:** 2026-04-23
**Applies to:** `ui/sift-ui/` (Leptos CSR) and `crates/sift-cli/src/tui/` (Ratatui)
**Builds on:** SP3 (time-partitioned storage + search `from`/`to`)

## Goal

Make the browser UI and terminal UI stop being tail-only. Both gain search, record detail, live-tail filter, help overlay, pause/resume, level quick-toggle, WebSocket auto-reconnect, and JSON syntax highlighting in the detail view. Everything lands in both clients in the same sub-project.

## Guiding principle (cross-cutting)

**Feature parity, platform-idiomatic rendering.** The UI and TUI must gain or lose features together, but *how* each client renders them follows platform convention. Clicky controls in the browser; modal keybinds in the terminal. This rule is codified in `[[CLI Overview]]` and `[[UI Overview]]` so future contributors don't re-litigate.

## Non-goals (deliberately out of scope)

- **CLI changes.** `sift search --from/--to` exists; `sift send`, `sift tail`, and the one-shot commands don't change.
- **API changes.** Everything uses endpoints shipped in SP2/SP3.
- **Streams view / plugins panel.** Need SP4 (catalog) and M4 (plugin host).
- **Shareable search URLs in the TUI** (obvious).
- **Server-side pagination cursor** (M2 SiftQL territory).
- **Syntax highlighting outside record detail** (log bodies stay plain text).

## Features

### 1. Navigation between tail and search

Both clients expose the same two views. Platform-appropriate shells:

| | UI | TUI |
|---|---|---|
| Primary chrome | Top sticky header with `Tail` / `Search` tab links, URL-backed (`/tail`, `/search`) | Single-view window; header line shows mode (`sift · tail` or `sift · search`) |
| Switch | Click tab OR `g t` / `g s` keybind OR browser back/forward | `t` → tail, `s` → search |
| Non-navigation keys | Vary per tab (see below) | Vary per mode (see below) |
| Help | `?` opens modal | `?` opens floating popup |
| Close overlay / return to tail | `Esc` | `Esc` |

UI URL scheme:
- `/` redirects to `/tail`.
- `/tail` — live tail.
- `/search?q=foo&from=2026-04-23T00:00:00Z&to=2026-04-23T01:00:00Z` — search with query string (shareable).

### 2. Search

#### UI

- Top of the search tab: three inputs side by side.
  - Query: `<input type="text">`, full-width.
  - From: `<input type="datetime-local">`.
  - To: `<input type="datetime-local">`.
- Quick-range buttons below the inputs: `Last 1h`, `Last 24h`, `Last 7d`. Clicking populates `from`/`to` and submits.
- Submit via **Search** button or `Enter` from any input.
- Results: scrollable table, one row per record, columns `time · host · app · level · body (truncated at 200 chars)`. Newest-first. Click a row → detail panel.
- Status line below the results: `42 results · scanned 10,482 · 310 ms`.

#### TUI

- Search mode has three stacked input fields: query, from, to. `Tab`/`Shift+Tab` cycles focus.
- Quick-range keys when no input is focused: `1` → last 1 h, `2` → last 24 h, `3` → last 7 d. Applies + submits immediately.
- Submit: `Enter` on the query field.
- Results pane below the inputs: same row format as tail (`ts host app level body`), Up/Down to navigate, `Enter` on a row opens the detail popup.
- Status line at the bottom: `42 results · scanned 10,482 · 310 ms` (mirrors the UI).

### 3. Record detail

Same information in both clients; rendered differently.

**Fields:**
- Header: `timestamp (RFC3339) · host · app · stream_id · level`.
- Body: full `body` string, wrapped.
- Labels: two-column table, keys sorted.
- Fields: JSON, pretty-printed, **syntax-highlighted** (see §9).
- Raw: preserved `_raw` if present, in a preformatted block.

**UI:**
- Right-side slide-in panel. Triggered by clicking any row (tail or search). ~40% of viewport width, full height.
- Closed via: `Esc`, clicking outside, or an explicit `×` close button in the panel header.
- Body of panel is scrollable independently from the underlying results.

**TUI:**
- Centered floating popup: 80% × 80% of terminal. Standard Ratatui `Clear` + `Block` pattern.
- Triggered by `Enter` on the selected row (tail or search).
- Closed via `Esc`.
- Contents scrollable via Up/Down when the popup has focus.

### 4. Client-side filter on live tail

Both clients: substring match against `record.body`, applied to records *after* they arrive from the WebSocket. Does not affect what the server sends; does not apply to search results (server already filtered by `q`).

- **UI:** filter input in the tail tab's header. Typing shrinks the list in real time; an `×` button clears.
- **TUI:** `/` focuses the existing tail filter bar (already implemented; unchanged).

When the filter is non-empty, the status pill shows `N matches · M filtered out`.

### 5. Help overlay

Press `?` in either client, anywhere (except inside a text input). Content: keybinding table for the current client.

- **UI:** modal dialog, centered, closes on `Esc` or click outside.
- **TUI:** centered floating popup, closes on `Esc`.

Contents generated from a shared table of bindings so they never drift out of sync with the implementation.

### 6. Pause / resume tail

- **UI:** toggle button in the tail tab's header. When paused, the button changes label to `Resume (42 new)`; clicking resumes and flushes queued records.
- **TUI:** `Space` toggles. Status line shows `[paused: 42 new]`. Pressing `Space` again (or `End`) flushes.

Behaviour in both:
- Incoming WebSocket records **are still received** while paused (to keep the server's broadcast channel drained — otherwise we'd lag out of the ring buffer).
- They queue in a separate pending buffer capped at 500 entries (same as the ring buffer).
- On resume, the pending buffer merges into the main ring buffer newest-at-bottom and the view refreshes.

### 7. Level quick-toggle

Level visibility is orthogonal to the substring filter — both apply.

- **UI:** a pill row near the filter: `Info · Warn · Error · Fatal` (click to toggle; greyed when hidden). `Trace`/`Debug` hidden by default behind a "More" expander.
- **TUI:** single-key toggles: `I` (info) / `W` (warn) / `E` (error) / `F` (fatal) / `D` (debug) / `T` (trace). Visible indicator in the status line: `[I W E F]` with dimmed letters for hidden levels.

Level visibility applies to the tail view AND the search results view (same widget pattern in both).

### 8. WebSocket auto-reconnect

Both clients gain an exponential-backoff reconnect loop on unexpected disconnect.

**States:** `Connecting → Connected → Disconnected → Reconnecting(attempt N) → (loop)`.

**Algorithm:**
1. On WS close / error: transition to `Reconnecting(1)`.
2. Delay `2^(N-1) * 1000 ms`, capped at `30 000 ms` (so: 1 s, 2 s, 4 s, 8 s, 16 s, 30 s, 30 s, …).
3. Try `WebSocket::new(...)`. On success: `Connected`, reset `N`. On failure: `Reconnecting(N+1)`, loop.
4. No attempt cap — keeps trying until the user navigates away / closes the process.

**Manual override:**
- **UI:** "Retry now" button appears next to the status pill when state is `Reconnecting` or `Disconnected`.
- **TUI:** `r` key triggers an immediate reconnect attempt.

**Status pill / line copy:**
- `connecting` (yellow) — initial attempt.
- `connected` (green) — happy path.
- `disconnected` (red) — terminal (happens if the WS crate signals we shouldn't retry, or user hit Ctrl+R in browser).
- `reconnecting (attempt 3, next in 4s)` (orange-ish) — active backoff.

**Records lost during reconnect** are lost — the WS broadcast channel doesn't replay. Users who need backfill run a search with `from=<disconnect_time>`.

### 9. JSON syntax highlighting in record detail

Both clients colorize the `fields` JSON display using the same token classes:

- **Key** — one color.
- **String value** — another color.
- **Number / Bool / Null** — a third color.
- **Punctuation** (`{`, `}`, `[`, `]`, `:`, `,`) — muted.

Platform implementations differ:

**UI:** inline tokenizer (~50 lines), produces a `Vec<(TokenKind, String)>` from a `serde_json::Value` via a tiny recursive walker. Leptos renders each token as a `<span class="json-key">` etc. with per-class CSS colors in `style.css`.

**TUI:** hand-rolled tokenizer at `crates/sift-cli/src/tui/jsonfmt.rs`. Pure function: `fn highlight(v: &serde_json::Value, indent: usize) -> Vec<Line<'static>>`. Each token becomes a `Span` with `Style::default().fg(color)`. No external dep (specifically NOT `syntect`, which is a heavy dep designed for full language grammars).

Color palette per platform:

| Token | UI (CSS var) | TUI (ratatui Color) |
|---|---|---|
| Key | `--accent` (green) | `Color::Cyan` |
| String | `--fg` (light) | `Color::Green` |
| Number/Bool/Null | `--warn` (yellow) | `Color::Yellow` |
| Punctuation | `--muted` (gray) | `Color::DarkGray` |

## Architecture

### UI (`ui/sift-ui/`)

Adds `leptos_router = "0.6"` (matching `leptos = "0.6"`).

New directory layout:

```
src/
├─ main.rs                   # mount + router setup
├─ app.rs                    # App root: header/tabs + <Outlet/> for routes
├─ routes/
│  ├─ mod.rs                 # <Route/> tree
│  ├─ tail.rs                # live tail view (moved from app.rs)
│  └─ search.rs              # NEW: search view
├─ components/
│  ├─ mod.rs
│  ├─ record_row.rs          # shared row rendering
│  ├─ record_detail.rs       # NEW: slide-in detail panel
│  ├─ filter_bar.rs          # NEW: substring filter
│  ├─ level_toggle.rs        # NEW: level pill row
│  ├─ time_range.rs          # NEW: from/to pickers + quick buttons
│  ├─ pause_button.rs        # NEW: pause/resume toggle
│  ├─ help_modal.rs          # NEW: ? overlay
│  ├─ status_pill.rs         # extracted, now renders Reconnecting state
│  └─ json_highlight.rs      # NEW: tokenizer + spans
└─ ws.rs                     # NEW: WebSocket connect + reconnect loop
```

Existing `app.rs` is ~150 lines; after the refactor it becomes ~60 (just the top-level shell).

### TUI (`crates/sift-cli/src/tui/`)

```
src/tui/
├─ mod.rs             # lifecycle + event loop (slight growth for mode dispatch)
├─ state.rs           # AppState grows a Mode enum + search state + level set
├─ view.rs            # draw(): dispatches to view_tail/view_search + overlays
├─ view_tail.rs       # NEW: tail rendering (moved from view.rs)
├─ view_search.rs     # NEW: search mode rendering
├─ view_detail.rs     # NEW: record detail popup
├─ view_help.rs       # NEW: help overlay
├─ jsonfmt.rs         # NEW: JSON tokenizer → Vec<Line>
├─ input.rs           # NEW: key dispatch by Mode + focus
└─ ws.rs              # + reconnect loop
```

`AppState` grows:

```rust
pub enum Mode { Tail, Search }
pub struct LevelSet { trace, debug, info, warn, error, fatal: bool }

pub struct AppState {
    // existing…
    pub mode: Mode,
    pub level_set: LevelSet,
    pub paused: bool,
    pub pending_while_paused: VecDeque<Record>,
    pub detail: Option<Record>,
    pub help_open: bool,

    // search
    pub search_q: String,
    pub search_from: String,    // user typed; parsed on submit
    pub search_to: String,
    pub search_focus: SearchFocus,  // Query | From | To
    pub search_results: Vec<Record>,
    pub search_scanned: usize,
    pub search_status: SearchStatus, // Idle | Running | Error(String)

    // reconnect
    pub status: ConnStatus,    // replaces the bool connected flag
}
```

### Shared concerns

- **Level visibility** and **substring filter** live in `AppState` (TUI) or context signals (UI). The render layer reads and filters.
- **Reconnect backoff** is client-local: the UI uses `gloo-timers` (already transitively via `leptos`); the TUI uses `tokio::time::sleep`.

## Error handling

| Scenario | UI behaviour | TUI behaviour |
|---|---|---|
| Search HTTP 4xx/5xx | Error banner above results with the server's message, "Retry" button | Red status line; Esc dismisses |
| Search timeout | Banner: `Search timed out — try narrowing the range` | Same copy in status line |
| Bad RFC3339 in from/to | Inline validation: invalid input flagged red | Status line: `invalid RFC3339 in "from"` at submit time |
| WebSocket dies mid-tail | Status pill → `reconnecting (attempt 1, next in 1s)` | Status line same copy |
| Reconnect gives up | Never gives up — infinite retry with 30 s cap | Same |
| Detail panel open while tail updates | New records still append in the background; panel stays open | Same |
| Pressing `?` while an input has focus | Ignored (literal `?` typed) | Ignored |

## Testing

### UI

Leptos CSR is hard to unit-test rigorously. Rely on:

- **Manual smoke matrix** captured in `ui/sift-ui/README.md`: open each route, exercise each keybind, confirm panel opens/closes, submit search, trigger reconnect by `nssm restart Sift`.
- **Server integration tests** already cover search correctness (`sift-server/tests/search.rs`). UI doesn't re-test the server.
- **Inline tokenizer unit tests** in `components/json_highlight.rs`: a pure function, easily tested in `#[cfg(test)]`.

### TUI

- **Pure state:** unit-test `AppState` transitions for each keybind in each mode. Existing tests (tail mode keys) stay; new tests for search-mode keys, level toggles, pause/resume buffering, reconnect state machine.
- **Pure views:** `view_tail::visible_range`, `view_search::visible_range`, `jsonfmt::highlight` → snapshot tests (exact `Vec<Line>` output for known inputs).
- **Integration:** existing tail WebSocket integration test stays. One new test drives the reconnect state machine by killing the server's broadcast channel; expects `Reconnecting(1) → Reconnecting(2) → …` transitions with expected delays.
- **No crossterm event-injection integration tests** — too flaky in CI. Manual smoke for full keybinding matrix.

## Rollout / deploy

- UI change ships via `trunk build --release` → IIS picks up `dist/` automatically. See `deploy.ps1`.
- TUI ships with the regular `sift-cli` build (users run `cargo install --path crates/sift-cli` or use `cargo run`).
- No server rebuild needed for UX v2.

## Open questions

None blocking. The "no attempt cap on reconnect" is a deliberate choice — a cap would mean the user comes back from lunch to a silently-dead UI, which is the exact problem reconnect is supposed to solve.
